# Research reporting

Every change and every experiment in this repository leaves a record. The
records are the raw material for the papers and the thesis: when a result is
written up months later, the question is always *what exactly was run, on what
data, and what did not work*, and that information is only cheap to capture at
the moment the work happens.

## Where the records live

The records are Markdown files in a **separate private repository**, mounted here
as the `reports/` submodule. Only the tooling and the schema are public:

```
src/reports/                  the library: parsing, validation, indexing
src/reports/schema.yaml       the single declaration of every field and section
src/reports/templates/        the scaffolds `report.py new` fills in
scripts/report.py             the CLI (new / validate / index / export)
ci/check_report_record.py     the CI guard: code changed => pointer moved
reports/                      the private submodule (records live here)
  changes/CHG-0001-*.md       one per pull request
  experiments/EXP-0001-*.md   one per experiment or analysis
  index.csv, metrics.csv      generated by `report.py index`
```

Get them with `git submodule update --init reports`. A clone without access to
the private repository still builds, tests and runs; only the report commands
need the submodule.

## The two kinds

**Change (`CHG`)** answers *what did this pull request do to the code*. **Experiment
(`EXP`)** answers *what did we run, on what data, and what came out*. A pull
request usually carries one change record, and zero, one or several experiment
records; an experiment that spans several pull requests stays one record whose
status moves from `planned` to `running` to `complete`.

## Writing one

```bash
uv run python scripts/report.py new experiment "Input-only Bragg-peak zone"
# edit the scaffolded file
uv run python scripts/report.py validate
```

The frontmatter holds everything machine-readable: ids, `data` sources with
sample counts and a leakage statement, `metrics` as `{name, value, unit, split,
n}` rows, `artifacts` paths, `compute` including the Monte Carlo seconds spent,
and the `publication` target this feeds. The body holds the narrative under nine
fixed headings, all required:

> What was done | Methodology | Data used | What precisely changed |
> Results: positive | Results: negative | What went well | What went wrong |
> Next steps

`Results: negative` is mandatory because negative results are the first thing to
evaporate and the most expensive thing to rediscover. `None.` is a valid answer
in any section; `TODO` is not, and the validator rejects it.

## Querying

```bash
uv run python scripts/report.py index      # index.csv, metrics.csv, index.db
sqlite3 reports/index.db "SELECT id, title, date FROM records WHERE tags LIKE '%active-learning%'"
sqlite3 reports/index.db "SELECT record_id, value FROM metrics WHERE name='labels_to_target' ORDER BY date"
uv run python scripts/report.py export --tag active-learning -o /tmp/chapter.md
```

`index.csv` also carries the git commit and dataset fingerprint pulled from the
`manifest.json` of any run directory a record names, where that directory is
reachable, which ties a reported number back to the code and data that produced
it.

## How this relates to the other logs

- **CHANGELOG.md** records public import paths and output formats under semantic
  versioning. It is for consumers of the code; the report records are for us.
- **`docs/`** holds design documents and plans, written before the work.
- **`research/`** holds finished, publication-shaped writing.
- The records hold what actually happened, including the parts that failed.
