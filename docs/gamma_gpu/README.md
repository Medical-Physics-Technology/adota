# GPU gamma index: results

Companion to [`gamma_gpu_results.md`](gamma_gpu_results.md), which is generated by
`uv run python scripts/gamma_benchmark.py report` and holds the tables. This file
is the reading of them.

Everything below was measured on one machine (3x NVIDIA A40, 48 cores, 376 GB,
driver 535.183.06) at Python 3.10.19 / pymedphys 0.41.0 / torch 2.8.0+cu128, over
the eight OpenTPS plan directories the brief names, five criteria each: 40
(plan x criterion) pairs.

## Acceptance

| comparison | pairs | tolerance | max abs delta | verdict |
|---|---|---|---|---|
| rung 2 vs rung 1 (the implementation) | 40 | 0.01 pp | **0.000000 pp** | PASS |
| rung 3 vs rung 2 (the device) | 40 | 0.001 pp | **0.000000 pp** | PASS |
| rung 4 vs rung 2 (float32) | 40 | 0.1 pp | 0.047677 pp | PASS |
| rung 3 vs rung 1 (not a brief gate) | 40 | 0.01 pp | **0.000000 pp** | PASS |
| rung 1 vs rung 0 | 40 | n/a | 0.056401 pp | reported, not gated |

The float64 torch backend reproduces `pymedphys.gamma`'s pass rate **exactly**, to
every digit the pass rate carries, on all 40 pairs, on CPU and on GPU alike. That
is a stronger result than the 0.01 pp gate asked for and it is worth being
suspicious of, so it is corroborated below by the voxel-level maps, which do
differ -- just far below the pass rate's resolution.

## Rung 1 vs rung 0, on its own

**The pymedphys 0.40 to 0.41 interpolator change moves the already-published
gamma pass rates.** Across the 40 pairs the shift is up to **0.056 pp** in
absolute value (mean 0.0075 pp), in both directions:

| plan | criterion | published (0.40) | re-run (0.41) | shift |
|---|---|---|---|---|
| LUNG1-195 Plan 2 | 1%/1mm/10% | 88.9720 | 89.0284 | **+0.0564** |
| LUNG1-062 Plan 1 | 1%/1mm/10% | 88.0980 | 88.0655 | **-0.0325** |
| Prostate-AEC-069 Plan 2 | 2%/2mm/10% | 96.8040 | 96.7782 | **-0.0259** |
| LUNG1-250 Plan 3 | 1%/1mm/10% | 63.5048 | 63.5048 | -0.0001 |

This is a finding about the existing results, not about the GPU work: it is the
same code path, on the same doses, with a different interpolator underneath. It
is well below the precision anyone quotes a GPR to, but it means the published
figures are reproducible to about 0.06 pp rather than exactly, and the tightest
criterion (1%/1mm) is where it shows. Two plans (LUNG1-062, Prostate-AEC-069)
account for most of it.

## Voxel-level parity

Pass rates can agree while the maps differ, so for the two plans whose gamma maps
were persisted the maps were compared voxel by voxel. The number that matters is
how many *evaluated* voxels cross the gamma = 1 decision boundary.

| comparison | max abs dgamma | 99.9th pct | gamma=1 crossings | evaluated-mask disagreements |
|---|---|---|---|---|
| rung 2 vs rung 1 (torch-CPU float64) | 1.19e-07 | 1.19e-07 | **0** | 0 |
| rung 3 vs rung 1 (GPU float64) | 1.19e-07 | 1.19e-07 | **0** | 0 |
| rung 4 vs rung 1 (GPU float32) | 9.5e-05 | 4.5e-05 | 0 to 106 per criterion (<= 3.8e-05 of evaluated) | 0 |

Two caveats on reading this:

* The persisted maps are float32, so 1.19e-07 is **one ulp at gamma = 1** -- the
  finest difference the stored maps can express. The true float64 difference is
  at or below that; it is not resolvable from these files.
* That 1.19e-07 floor is not rounding noise, it is a real and explainable
  difference. See below.

## The one thing not reproduced exactly

`pymedphys`'s `calculate_min_dose_difference` allocates its per-shell minimum
relative dose difference as

```python
min_relative_dose_difference = np.nan * np.ones_like(options.flat_dose_reference[to_be_checked])
```

`flat_dose_reference` is whatever dtype the caller's dose is -- **float32** for
every dose in this pipeline, since `load_dose_gy` returns float32. The minimum is
computed in float64 and then quantised to float32 on assignment into that array.

`gamma_torch` keeps it at the working dtype. The consequence is a systematic
~1e-7 difference in gamma whenever the input doses are float32, and it is the
entire residual: feed both implementations float64 doses and they agree to
**1.2e-14**, which is float64 rounding of the same expression.

This was **not** replicated. Reproducing it would mean deliberately rounding an
intermediate to float32 inside a float64 code path, which would defeat the
float64 mode and bake a precision artifact of one implementation into another.
The cost of not replicating it is bounded and measured: zero gamma = 1 boundary
crossings across 9.3 M evaluated voxels, and an exactly zero change in all 40
pass rates.

If exact bit-parity with pymedphys on float32 input ever becomes a requirement,
it is one cast in `min_dose_difference`, not a redesign.

## Performance

One A40, one GPU only, warm-up excluded from every timed region.

| rung | what | total wall time, 8 plans x 5 criteria | vs rung 1 |
|---|---|---|---|
| 0 | recorded `gamma_metrics.json` | 14873.4 s (4.13 h) | *provenance only* |
| 1 | pymedphys 0.41, this machine | **3016.0 s (50.3 min)** | 1.0x |
| 2 | gamma_torch, torch-CPU, float64 | 1767.9 s (29.5 min) | 1.7x |
| 3 | gamma_torch, one A40, float64 | **159.0 s (2.65 min)** | **19.0x** |
| 4 | gamma_torch, one A40, float32 | 111.3 s (1.86 min) | 27.1x |

**The 4.13 h figure is provenance, not a controlled measurement** -- another
machine, under unknown load, on pymedphys 0.40 and Python 3.9. No speedup is
computed against it. The controlled comparison is rung 3 against rung 1: the same
machine, the same day, the same pymedphys, nothing else running.

Most of the 4.13 h to 50 min gap is pymedphys's own 0.40 to 0.41 interpolator
change, which is roughly a 4.9x speedup on its own and costs nothing to take.

Warm-up (CUDA context plus first kernel) is **~1.0 s**, paid once per process,
and is excluded from every timed region above.

Peak device memory is **2.1 to 2.8 GiB** across all eight plans in float64, on
grids from 67.5 M to 100.5 M voxels. It was 10 to 33 GiB until a reference cycle
in the interpolation recursion was found and removed; see the commit
"Stop the interpolation temporaries leaking through a closure cycle". Anyone
reading an earlier draft of these numbers should discard the memory column.

## What is not covered

* **Scalar thresholds only.** `pymedphys.gamma` accepts sequences and answers
  with a dict of gamma arrays; `gamma_torch` raises `NotImplementedError`. Every
  criterion in this corpus is scalar.
* **`local_gamma` is not exercised by the corpus** -- all 40 recorded criteria are
  global. It is covered against `pymedphys.gamma` on synthetic cases in
  `tests/test_gamma_torch.py`, including the `lower_percent_dose_cutoff=0` case
  where it divides by zero-dose voxels.
* **Uniform grids only**, checked on entry. Both grids in this pipeline are
  uniform by construction.
* **One GPU.** Three A40s are present; nothing here shards across them.
* The torch backend is **opt-in and not the default**. It should run alongside
  the pymedphys path on real validation data before that changes.
